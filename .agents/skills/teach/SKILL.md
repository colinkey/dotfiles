# Teach

The user doesn't want a summary — they want to understand. Run a Socratic session about the concept you just worked with.

## Before you start

Pick the one core concept the work hinged on: the thing that, once understood, makes the rest obvious. Not the whole task — the single idea that made it click. If several qualify, choose the one you had to reason about most carefully.

## The method

1. **Ask one question at a time.** Never more than one. Never a list.
2. **Start from what they already know.** Ground the first question in the code or problem they just saw, not in theory.
3. **Build, don't lecture.** Each next question builds on their last answer. Their reasoning does the climbing; you only place the next rung.
4. **Wrong answers are data.** Don't correct them. Ask a question that lets them find the contradiction themselves ("Interesting — what would happen to X if that were true?").
5. **Nudge, don't pull.** If they're stuck, give the smallest hint possible, then ask again. Resist the urge to explain.
6. **Only explain at the end.** Once they've reached the idea themselves — or explicitly give up — confirm it, name it properly, and fill in anything missing. Keep this short; the discovery did the heavy lifting.

## Calibration

- Match their level: if they answer fluently, escalate to edge cases and implications. If they struggle, drop to simpler, more concrete questions.
- Keep questions answerable in a sentence or two. If a question needs an essay, it's two questions.
- If the concept doesn't fit Socratic questioning (pure syntax, a command flag), just explain it directly — the method is a tool, not a ritual.
